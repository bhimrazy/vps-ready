vps-ready groups its changes into **modules**, and a **profile** picks which modules run. You choose one with `--profile`, or pick modules one by one with `--module`. This page compares the built-in profiles, shows how to write your own, and lists what each module writes, checks first and undoes.

## Pick a profile

| | Plain `apply` | `--profile minimal` | `--profile web` | `--profile private` + a VPN module |
|---|---|---|---|---|
| Admin user (`user.admin`) | | yes | yes | yes |
| SSH server config (`ssh.server`) | | yes | yes | yes |
| Firewall (`firewall.inbound`) | | SSH only | SSH, 80/tcp, 443/tcp, 443/udp | SSH through a VPN only |
| fail2ban (`ssh.bruteforce`) | | | yes | yes |
| Docker (`deploy.docker`) | | | yes | |
| Kernel settings (`kernel.sysctl`) | yes | yes | yes | yes |
| Automatic updates (`updates.auto`) | yes | yes | yes | yes |
| Asks for a confirm | no | yes | yes | yes |

- **Plain `apply`**, with no `--profile` or `--module`, only changes kernel settings and automatic updates. Nothing in it can lock you out, so a future version can never make a plain `apply` start changing SSH or the firewall.
- **minimal** is for any server you log into over SSH.
- **web** is minimal plus the web ports (UDP 443 is for HTTP/3), fail2ban and Docker with safe defaults.
- **`net.tailscale` and `net.wireguard` are in no built-in profile.** Add one in your own profile; see [Tailscale](#nettailscale-tailscale) and [WireGuard](#netwireguard-wireguard) below.
- **`net.tunnel` is in no built-in profile.** Add it in your own profile; see [Cloudflare Tunnel](#nettunnel-cloudflare-tunnel) below.
- **private** is for a server with no public SSH: SSH only through a VPN, and no public port unless you add one. It names no VPN, so you extend it; see [The private profile](#the-private-profile) below.
- **`deploy.proxy` (Caddy) and `deploy.user` are in no built-in profile.** They need values only you have (domains, deploy keys), so you add them in your own profile, or the guided setup adds Caddy when you give it a domain. See [Deploy an app](/docs/guides/deployment-modules/).

`sudo vps-ready` with no arguments recommends `minimal` or `web` for you, offers `private` through its private access question, and builds the profile from your answers: see the [quick start](/docs/quick-start/). To read what a module does before choosing, run `vps-ready modules` (or `vps-ready modules ssh.server` for one).

To see exactly what would change on your server, run `plan` with the same flags first:

```sh
sudo vps-ready plan --profile web
```

## Write your own profile

A profile is a TOML file that can extend `minimal`, `web` or `private`, change a module's settings, or leave a module out:

```toml title="my-server.toml"
schema  = 1
extends = "web"

[modules."user.admin"]
name            = "deploy"
authorized_keys = ["ssh-ed25519 AAAAC3Nza... me@laptop"]
sudo            = "nopasswd"     # or "password"

[modules."firewall.inbound"]
allow = ["22/tcp", "443/tcp"]

[modules."ssh.bruteforce"]
enabled = false

[modules."deploy.proxy"]
sites = [{ domain = "app.example.com", upstream = "127.0.0.1:8080" }]
```

Check it with `plan` first:

```sh
sudo vps-ready plan --profile ./my-server.toml
```

A typo in a key is an error that names the module, not a silently ignored line. `sudo = "password"` only works for an account that already has a password; vps-ready never asks for or sets one.

## The order modules run in

| Order | Module | Safety net | Why it sits here |
|---|---|---|---|
| 1 | `user.admin` | yes | Creates the way in that is not root |
| 2 | `ssh.server` | yes | Turns off root and password logins, and refuses unless that way in exists |
| 3 | `net.tailscale` | under `ssh_via` on Tailscale | Before the firewall: a private path to SSH that needs no open port |
| 4 | `net.wireguard` | under `ssh_via = "wg0"` | Before the firewall, which opens its UDP port |
| 5 | `net.tunnel` | no | Before `deploy.proxy`, which reads whether a tunnel is planned |
| 6 | `deploy.docker` | no | Before the firewall, so the firewall knows Docker's bridges |
| 7 | `firewall.inbound` | yes | Drops unsolicited traffic, always allowing the SSH ports in use |
| 8 | `ssh.bruteforce` | no | Can only ban an address, and never yours |
| 9 | `kernel.sysctl` | no | Cannot lock you out |
| 10 | `updates.auto` | no | Cannot lock you out |
| 11 | `deploy.proxy` | no | After the firewall, so it can read whether ports 80 and 443 are open |
| 12 | `deploy.user` | no | Last: a login for CI, separate from the admin |

The order is fixed. The admin user comes first because turning off root and password logins is only safe once there is another way in, and the firewall comes after the admin user and SSH so it can allow the SSH port your login really uses. On their own, the three deployment modules do not touch the SSH server, the firewall's SSH rule or the admin's login, so they do not arm the safety timer. In a run with a guarded module, as in the `web` profile, they share its transaction: confirm it, or the timer undoes them too. The three guarded modules share one transaction, so a single new login confirms all of them together. To see which part fails on a tricky server, apply `--module user.admin` on its own first, then the rest.

## The modules

Every module reads the live state first, plans only what fails, and writes files it owns. A second `apply` finds nothing to do.

### `user.admin`: the admin user

**Changes:** creates an admin user named `admin` (or completes an existing one), adds your SSH keys to its `~/.ssh/authorized_keys`, and gives it sudo with `/etc/sudoers.d/90-vps-ready-admin` (`admin ALL=(ALL:ALL) NOPASSWD: ALL`, as cloud images do for their default user).

**Keys:** without keys in a profile, it copies the keys of the account you logged in with. Key lines with options such as `command=` are skipped, since they would restrict the admin too.

**Checks first:** it refuses when the name is `root`, when an existing account is a system account (uid below 1000, or a shell not listed in `/etc/shells`), when sudo is not installed, when there are no keys to copy, or when sshd's `AuthorizedKeysFile` does not include `.ssh/authorized_keys`, where it writes the keys (sshd would ignore them). An account that already has sudo rules keeps them, and no sudoers file is written.

**Undo:** rollback removes a user it created but keeps its home directory, so the change is labeled `partial`. Keys it added and the sudoers file are restored exactly.

### `ssh.server`: the SSH server config

**Changes:** writes one drop-in, `/etc/ssh/sshd_config.d/00-vps-ready.conf`, and reloads the SSH server. It sets each of these to `no`, but only the ones that fail today:

`PermitRootLogin` · `PasswordAuthentication` · `KbdInteractiveAuthentication` · `PermitEmptyPasswords` · `X11Forwarding` · `HostbasedAuthentication` · `PermitUserEnvironment`

It never touches `Port`, `ListenAddress`, `AllowGroups`, `AuthenticationMethods` or the crypto settings, and it never edits `sshd_config` itself or any `Match` block. A `Match` block that sets one of these keywords wins over the drop-in for the connections it matches: the plan notes it, and the audit keeps failing that control until you change the block. The SSH port stays 22. The `00-` name makes it win over cloud-init's `50-cloud-init.conf`, which turns passwords back on.

**Checks first:** it refuses to turn off root or password logins unless a user other than root has an SSH key and sudo: the admin from `user.admin`, or the user you are logged in as. It also checks that `sshd_config` reads the drop-in before anything that could override it. After the reload, it verifies the effective config with `sshd -T` for the admin's own connection.

**Undo:** the drop-in is removed (or restored) and the SSH server is reloaded. SSH sessions that are open stay open throughout.

### `firewall.inbound`: the firewall

**Changes:** installs `nftables` if it is missing, writes its own table `inet vps_ready` to `/etc/vps-ready/firewall.nft`, and loads it with its own `vps-ready-firewall.service`. The table drops incoming traffic that no rule allows and accepts replies, loopback, ICMP (including all of ICMPv6), DHCP, and the profile's ports.

It also drops incoming IPv4 TCP packets that carry IP options, in a `prerouting` chain that runs before connection tracking and also covers traffic forwarded to containers. This blunts [CVE-2026-98432](https://ubuntu.com/security/CVE-2026-98432), a kernel use-after-free in the TCP handshake; the fix is a kernel update and a reboot ([Debian](https://security-tracker.debian.org/tracker/CVE-2026-98432), [Ubuntu](https://ubuntu.com/security/CVE-2026-98432)). Other IPv4 protocols keep their options (IGMP uses one), and IPv6 is not affected by the bug. If you label traffic with CIPSO (NetLabel), TCP over IPv4 stops working. A host that keeps ufw or firewalld gets no such rule; follow your distro's guidance linked above instead.

**Checks first:** it always accepts every SSH port in use (your session's, the SSH server's listeners and its `Port`), whatever the profile says. It is not applied while ufw or firewalld is active, or when it cannot read the current rules. See [Use it on a server that's already running things](/docs/guides/existing-server/).

**Undo:** rollback deletes only the `inet vps_ready` table and its unit, so Docker's and fail2ban's rules stay. If it installed `nftables`, the package stays installed.

**SSH only through a VPN (`ssh_via`):** with `ssh_via = "wg0"` (or `"tailscale0"`, or any interface you set up), the SSH rule accepts only packets that arrive on that interface, over IPv4 and IPv6; everything else stays as above, and SSH ports listed in `allow` are left out with a note. The SSH server itself is not changed.

It is a second apply, walked through in [Close public SSH](/docs/guides/private-access/#close-public-ssh): set up the VPN first, log in through it, and apply `ssh_via` from that session. It is refused when the interface is missing, down or has no address, when the session does not come through it, when the VPN would not come back after a reboot (`wg-quick@wg0` or `tailscaled` not enabled), when a Tailscale node key expires, for `lo`, Docker's and other local bridges or the default route's interface, and with `--deadman=off`. The confirm must then come from a new login through the same interface, from another machine.

Apply `firewall.inbound` without `ssh_via` first: a public session opened while no firewall was loaded is not tracked as established, so the `ssh_via` apply can drop it. While SSH depends on the VPN, a change that arms the safety timer needs a confirm through it, so one applied from the console while the VPN is down rolls back. Set a password for a sudo user first if you want your provider's web console as a way back in (see [Undo changes and recover](/docs/guides/undo-and-recover/)).

```toml
[modules."firewall.inbound"]
allow = ["80/tcp", "443/tcp"]
ssh_via = "wg0"
```

#### The private profile

`private` has the `web` hardening without Docker, an empty `allow`, and `ssh_via = "vpn"`: the interface of the one VPN module in your profile (`tailscale0` for `net.tailscale`, `wg0` for `net.wireguard`). On its own, or with two VPN modules, it is refused, so extend it with one:

```toml title="private.toml"
schema  = 1
extends = "private"

[modules."user.admin"]
authorized_keys = ["ssh-ed25519 AAAAC3Nza... me@laptop"]

[modules."net.tailscale"]
```

Apply the same file twice. The first apply, from a public SSH login (or at first boot from `export cloud-init`), sets up the VPN and keeps SSH public, with the note "step 1 of 2: SSH stays public until you apply this profile again from a login through tailscale0". Then log in through the VPN and run the same command: from that session, `ssh_via = "vpn"` closes public SSH exactly like an explicit `ssh_via`, with its checks, the safety timer and the confirm through the VPN. After that, applying the file again changes nothing. If SSH is already limited to another interface, the first step is refused rather than reopening SSH publicly. Add `"80/tcp", "443/tcp", "443/udp"` to `allow` for a web app.

### `ssh.bruteforce`: fail2ban (web profile)

**Changes:** installs `nftables`, `python3-systemd` and `fail2ban`, writes `/etc/fail2ban/jail.d/90-vps-ready.local` to turn on the `sshd` jail (reading the systemd journal, banning in nftables on the ports sshd listens on), and restarts fail2ban. It sets nothing for your other jails.

**Checks first:** the address of the SSH session running `apply` is never banned, nor is localhost. For the `sshd` jail, this list replaces any `ignoreip` your `jail.local` sets.

**Undo:** the jail file is restored, but packages are never removed, so fail2ban stays installed and enabled and runs the distro's own jails. `systemctl disable --now fail2ban` turns it off.

fail2ban is only in the web profile because, once SSH takes keys only, brute-force attempts are mostly log noise, and OpenSSH 9.8 and later already slows them down with `PerSourcePenalties`.

### `kernel.sysctl`: kernel settings

**Changes:** sets safer kernel and network settings at runtime and keeps them across reboots in `/etc/sysctl.d/90-vps-ready.conf`: hidden kernel pointers and logs, restricted BPF, ptrace and perf, protected links, FIFOs and files in shared directories such as `/tmp`, full address space randomization, no setuid core dumps, SYN cookies, no source-routed packets, ignored broadcast pings, and Multipath TCP off.

**Checks first:** only failing settings are changed, so a stricter value your distro already uses stays. It never sets `ip_forward=0`, which would break Docker. Inside a container it does nothing, since the settings belong to the host.

**Undo:** the drop-in is removed and each setting gets its old value back. If the server rebooted since `apply`, the running values stay until the next boot, which reads the restored files.

### `updates.auto`: automatic security updates

**Changes:** installs `unattended-upgrades` and writes `/etc/apt/apt.conf.d/52vps-ready`, which turns on apt's daily package list update and unattended upgrade. Automatic reboots are left to you.

**Checks first:** Debian and Ubuntu only. If apt's systemd timers are turned off, the plan says so and leaves them off.

**Undo:** the drop-in is removed; the package stays installed.

### `net.tailscale`: Tailscale

**Changes:** installs `tailscale` from Tailscale's repository (its key is built into vps-ready, fingerprint `2596 A99E AAB3 3821 893C 0A79 458C A832 957F 5868`), enables and starts `tailscaled`, and with `auto_update = true` (the default) writes `/etc/apt/apt.conf.d/52vps-ready-tailscale` so that `updates.auto` installs Tailscale's updates too. Each update restarts `tailscaled`, which drops tailnet connections for a moment; SSH sessions over it resume.

```toml
[modules."net.tailscale"]
auth_key_file = "/root/tailscale-auth-key"     # optional
login_server  = "https://headscale.example.com" # optional
hostname      = "web-1"                         # optional
```

With `auth_key_file`, it logs in with `tailscale up --auth-key=file:<path> --accept-dns=false`: `tailscale` reads the key, so it never appears in vps-ready's plan, journal or the process list. The file must be owned by root with mode `0600`, not be a symlink, and sit in directories only root can write to. Delete it after the login: from then on the node logs in with its own node key, also after a rollback, even with `auth_key_file` removed from the profile. If that login has expired or the node was removed from the tailnet, the apply fails and says so: put a new key in `auth_key_file`. Use a one-off or pre-approved key, tagged and not ephemeral: a tagged node has key expiry turned off, and an ephemeral node is removed from the tailnet when it goes idle. On a tailnet with device approval, a key that is not pre-approved makes the login time out, and a one-off key is then spent. vps-ready cannot see which kind of key it is. Without `auth_key_file`, log in once with `sudo tailscale up --accept-dns=false`.

**Under `ssh_via`:** while the loaded firewall accepts SSH only on Tailscale's interface, any change this module makes arms the safety timer and needs a confirm through Tailscale, and the dead-man rollback restores its files even if edited since. Nothing it plans stops `tailscaled` or takes a running node down, and the wizard says the timer may arm.

**Checks first:** Debian and Ubuntu with systemd only. A node that is already logged in is left as it is, and the plan names settings it has that vps-ready would not set (accepted DNS, an exit node, Tailscale SSH). vps-ready never turns on Tailscale SSH, which would replace sshd's keys and settings with the tailnet's policy, and never accepts the tailnet's DNS. No firewall port is opened: Tailscale needs none.

**Undo:** the repository, its key and the origin file are removed; `tailscale down` runs if the node was not up before, and `tailscaled` is stopped if it was off before. On a fresh install, `tailscaled` keeps running after the rollback, as the package started it: `sudo systemctl disable --now tailscaled` stops it. The package, `/var/lib/tailscale` and the node's login stay: `sudo tailscale logout` removes the node from the tailnet. A rollback that would stop `tailscaled` or run `tailscale down` is refused before it changes anything: while `ssh_via` limits SSH to Tailscale, whatever the session (remove `ssh_via` or roll back the transaction that set it first), and otherwise from an SSH session that comes through Tailscale (roll back from the provider's console or a public SSH login).

`export cloud-init` refuses a profile with `auth_key_file`: user-data can be read through the metadata service, so it must not lead to a key.

### `net.wireguard`: WireGuard

**Changes:** installs `wireguard-tools`, generates the server's private key in `/etc/wireguard/wg0.key` (mode 0600) with `wg genkey` writing straight to the file, writes `/etc/wireguard/wg0.conf` and a drop-in for `wg-quick@wg0`, and enables and starts `wg-quick@wg0`. It is for admin access to this host only: peers reach its tunnel address and nothing else, with no forwarding, routes or NAT.

```toml
[modules."net.wireguard"]
port = 51820                     # default
address = "10.86.12.1/24"        # optional; derived per server by default
endpoint = "203.0.113.10"        # optional; only for the printed client config
peers = [
  { name = "laptop", public_key = "<from wg pubkey on the laptop>", host = 2 },
]
```

Each device makes its own key (`wg genkey | tee laptop.key | wg pubkey`, or "Add tunnel" in the WireGuard app) and you list its public key; `host` is the last part of its tunnel address, from 2 to 254. Without `address`, the subnet is a `/24` in `10.0.0.0/8` derived from `/etc/machine-id`, with the server at `.1`, so each server gets its own and one laptop can reach several. A subnet that overlaps an address or route on the server is refused. After apply, and any time with `sudo vps-ready wireguard-config [PEER]`, vps-ready prints each device's client config, with a placeholder where the device's own private key goes.

The private key never passes through vps-ready: `wg0.conf` holds no `PrivateKey`, its `PostUp` loads the key file, and the plan, the journal and the transaction's file copies never contain it. A running `wg0` changes with `wg set` only. The unit's own reload runs `wg syncconf`, which clears a key loaded by `PostUp`, so the drop-in empties `ExecReload=`: `systemctl reload wg-quick@wg0` fails instead. Someone who ran `wg set` by hand shows up as a change in the next plan, which puts `wg0` back to the file. Changing `address` on a running `wg0` is refused: stop it with `sudo systemctl stop wg-quick@wg0` and apply again, from public SSH or the console. `firewall.inbound` accepts its UDP port.

**Under `ssh_via = "wg0"`:** any change this module makes arms the safety timer and needs a confirm through `wg0`, and the dead-man rollback restores it even if edited since. From a session through `wg0`, removing that session's own peer, or changing its key or `host`, is refused.

**Checks first:** Debian and Ubuntu with systemd, and a kernel with WireGuard (not in LXC or OpenVZ containers). A `wg0.conf` or a `wg0` interface that vps-ready did not make is left alone; `ssh_via = "wg0"` works with it.

**Undo:** the config, the drop-in and the unit's state are restored, and peers it changed on a running `wg0` are put back with `wg set`. The generated key stays, so client configs made meanwhile keep working: `sudo rm /etc/wireguard/wg0.key` and apply again for a new one. A rollback that would stop `wg-quick@wg0` is refused while `ssh_via` limits SSH to `wg0`, and one that would stop it or remove your session's peer is refused from a session through `wg0`: roll back from public SSH or the provider's console.

`export cloud-init` warns about an explicit `address`, which every server made from it would share.

### `net.tunnel`: Cloudflare Tunnel

**Changes:** installs `cloudflared` from Cloudflare's repository (suite `any`; its key is built into vps-ready, fingerprint `CC94 B39C 77AE 7342 A68B 8962 8A68 2D30 8D4E 5E73`), and with `auto_update = true` (the default) writes `/etc/apt/apt.conf.d/52vps-ready-cloudflared` so that `updates.auto` installs cloudflared's updates too. With `token_file`, it writes and starts `vps-ready-cloudflared.service`, the connector, with its config `/etc/vps-ready/cloudflared.yml`, and `vps-ready-cloudflared-restart.path`, which restarts the connector on the new binary after each upgrade (the package restarts nothing itself).

```toml
[modules."net.tunnel"]
provider = "cloudflare"                 # the only value
token_file = "/root/cloudflared-token"  # optional
auto_update = true                      # default
```

Create the tunnel in the Cloudflare dashboard (a remotely-managed tunnel: its routes live at Cloudflare, and the host needs only its token), save the token to a file owned by root with mode `0600`, not a symlink, in directories only root can write to, and set `token_file`. The token never passes through vps-ready: the unit's `LoadCredential=` copies the file at each start into a directory only the connector can read, and the plan, the journal and the process list never contain it. After replacing the file, run `sudo systemctl restart vps-ready-cloudflared`. Then give the tunnel a published route for each site in the dashboard, to a loopback address such as `http://127.0.0.1:80`; the plan says so. Without `token_file`, only `cloudflared` and the update origin are installed.

The connector runs as a fresh unprivileged user (`DynamicUser=yes`) with a sandbox, and `IPAddressDeny=` keeps it off link-local addresses (the cloud metadata service), private ranges and Azure's platform address, except the resolvers in `/etc/resolv.conf` at apply time: apply again when they change. Inside a container, or without cgroup BPF, systemd does not enforce that filter, and the plan says so. Its start is the check: the unit starts only once cloudflared has a connection to Cloudflare's edge (outbound port 7844), so a bad token or a blocked port fails the apply, which rolls back. Verify then runs `cloudflared tunnel ready` against the metrics address `127.0.0.1:20241` and checks the connector runs the installed binary. No inbound port is opened.

**Trust:** whoever controls the Cloudflare account can add a route from the internet to any address the connector reaches on loopback, SSH included, which the inbound firewall does not see. Turn on two-factor login for the account, and add no routes but the web ones. While a connector runs, `SSH-009` says so in its finding.

**Checks first:** Debian and Ubuntu with systemd. A `cloudflared.service` from Cloudflare's own install, or another cloudflared unit, is left alone. A `cloudflared` older than 2025.4.0 (which `--token-file` needs) and another listener on `127.0.0.1:20241` are refused.

**Undo:** the connector, the path unit, their files, the repository, its key and the origin file are removed. The package and the token file stay; the tunnel then shows as down in the dashboard, where deleting it is up to you.

`export cloud-init` refuses a profile with `token_file`, as for Tailscale's `auth_key_file`.

### `deploy.docker`, `deploy.proxy` and `deploy.user`: deployment

**Changes:** `deploy.docker` installs Docker Engine from Docker's repository and writes `/etc/docker/daemon.json`; `deploy.proxy` installs Caddy and writes a `Caddyfile` with one block per site; `deploy.user` creates a login account for CI whose keys are restricted. `deploy.docker` is in the `web` profile; the other two need your domains or keys.

**Checks first:** each says in the plan what it will do and refuses what it cannot do safely, for example Docker from the distro's `docker.io` package, or a `Caddyfile` you wrote by hand.

**Undo:** config files are restored or removed and package sources removed, and packages stay installed. `deploy.user`'s account is removed, and its home directory stays. Caddy is stopped and disabled when there was no `Caddyfile` before.

The details, with the commands and what to expect, are in [Deploy an app](/docs/guides/deployment-modules/).
