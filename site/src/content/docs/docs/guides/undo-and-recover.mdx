Every `apply` is one **transaction**, journaled in `/var/lib/vps-ready`. You can undo it at any time, whether or not the safety timer is still running. This page shows how, and how to get back into a server you can no longer log in to.

Before your first profile apply, check that your provider's web console works and that you can log in there, and take a provider snapshot. Neither is needed if all goes well, but each gives you a way back if SSH stops working.

## Undo the last apply

To undo the most recent apply, run:

```sh
sudo vps-ready rollback --last
```

`--last` picks, in this order: an apply that was interrupted part way, then one that is waiting for a confirm, then the newest one that was applied or confirmed. The rollback prints each step and a summary:

```text
remove /etc/apt/apt.conf.d/52vps-ready
restore net.ipv4.conf.all.accept_source_route = 1
restore fs.protected_regular = 0
restore fs.protected_fifos = 0
restore kernel.unprivileged_bpf_disabled = 0
restore kernel.dmesg_restrict = 0
restore kernel.kptr_restrict = 0
remove /etc/sysctl.d/90-vps-ready.conf
Rolled back transaction 20261023T190556Z: restored 8 changes.
```

Rolling back a transaction that waits for a confirm also stops its safety timer.

## Undo an older apply

To pick a transaction by ID, list them first, newest first:

```sh
sudo vps-ready history
```

```text
20261024T081500Z      applied                        kernel.sysctl,updates.auto  8 changes
20261023T190556Z      rolled-back (manual)           kernel.sysctl,updates.auto  8 changes
```

Then roll back the one you want:

```sh
sudo vps-ready rollback --txn 20261024T081500Z
```

`history --json` prints the same list for scripts.

## What a rollback leaves

Some things stay on purpose. Installed packages (`nftables`, `fail2ban`, `unattended-upgrades`, and Docker's and Caddy's) stay installed, and a created admin user's home directory stays, in case it holds your files. The plan labels these changes `partial`.

Rolling back `deploy.docker` restores `daemon.json` (it removes the file only if the apply created it), removes Docker's apt source and key if the apply added them, then restarts Docker if it is running; a stopped Docker stays stopped. If `live-restore` was off before, that restart stops the running containers a second time (the apply stopped them once), and only those with a restart policy start again. `apply` listed them in its plan.

Rolling back `deploy.proxy` restores the `Caddyfile` that was there before and reloads Caddy. Only when there was none does it remove the file, then stop and disable Caddy, since it cannot run without one. Both modules leave their packages. Details: [Deploy an app](/docs/guides/deployment-modules/#what-a-rollback-leaves-behind).

## When rollback refuses

A manual rollback is all or nothing, so it refuses (exit code 2) rather than undo half a transaction:

- **A file changed since `apply`.** vps-ready will not overwrite an edit you made after it. Put the file back, or undo your edit, and run it again.
- **It would remove your own account.** You cannot roll back the admin user while you are logged in as that user. Log in as another user with sudo.
- **A later apply depends on it.** An admin user cannot be removed while a later transaction is applied, confirmed or waiting, since that one may have turned off root and password logins. Roll back the later one first.
- **SSH depends on a VPN (`ssh_via`).** A rollback that would limit SSH to the VPN again runs only from an SSH login through the VPN, from another machine, since no timer covers it. One that would stop `tailscaled` or take the node off the tailnet is refused while SSH or your own session depends on Tailscale. The message says which path to use. See [Private access](/docs/guides/private-access/#if-the-vpn-stops-working).

If a rollback starts but cannot finish, it exits 3 and says what is left to do by hand, for example when `userdel` fails because the admin user still has processes running.

## Get back in after an SSH lockout

If you cannot log in, work down this list. **If you just ran `apply` with a profile and have not confirmed yet, the safety net is still armed**, so the first step may be all you need:

<Steps>

1. **Wait for the timer.** If the change is still waiting for a confirm, it rolls back on its own at the deadline (5 minutes by default). Then log in the way you did before.

2. **Use a session that is still open.** The terminal you ran `apply` in keeps working after the change. From there, run:

   ```sh
   sudo vps-ready rollback --last
   ```

3. **Reboot from your provider's control panel.** If the change has not been confirmed, a reboot rolls it back before the SSH server starts. After a confirm, a reboot changes nothing: the changes are kept.

4. **Use your provider's web console** (or serial console). It logs in locally, without SSH or the firewall. Run `sudo vps-ready rollback --last` there. The console cannot confirm a change, but it can roll one back. The console needs a password, so set one for a sudo user (`sudo passwd admin`) before you close public SSH.

   If SSH goes only through a VPN (`ssh_via`) and the VPN is down, roll back the `ssh_via` change by its ID. This reopens public SSH and keeps the firewall loaded:

   ```sh
   sudo vps-ready history
   sudo vps-ready rollback --txn <id>
   ```

   If the rollback refuses, remove `ssh_via` from your profile, apply from the console, and confirm from a new public login. Stopping the firewall (`sudo systemctl stop vps-ready-firewall`) is the last resort: it drops every rule until the next boot, so run `sudo systemctl start vps-ready-firewall` once you are back in. From the console while the VPN is down, a change that arms the safety timer cannot be confirmed and rolls back at its deadline, unless the change removes `ssh_via`. Details: [Private access](/docs/guides/private-access/#if-the-vpn-stops-working).

5. **Last resort: the provider's rescue system.** Each transaction keeps what it wrote and the original files in `/var/lib/vps-ready/txn/<id>/`: `journal.jsonl` lists every change, and `files/<n>.before` holds the original bytes, so you can put files back by hand from a mounted disk.

</Steps>

If vps-ready ever leaves you locked out, that is a security bug. Please [report the lockout](https://github.com/bhimrazy/vps-ready/issues/new?template=lockout_report.yml), or for anything sensitive use [private vulnerability reporting](https://github.com/bhimrazy/vps-ready/security/advisories/new).
