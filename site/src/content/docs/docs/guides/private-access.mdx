A new server answers SSH to the whole internet. This guide narrows that to your own devices in three steps, and shows how to get back in if the private network fails.

First, [harden the server at first boot](#harden-at-first-boot), before anyone logs in. Next, [join a private network](#join-a-private-network) such as Tailscale or WireGuard, so you can reach the same SSH server through it. Last, [close public SSH](#close-public-ssh-port-22-to-the-internet) from a login that already comes through that network.

Each step works on its own. If the server is already running, skip the first.

## Harden at first boot

`vps-ready export cloud-init` turns a profile into user-data that you paste into your provider's form when you create a server. At first boot it installs this version of vps-ready, checks the tarball's SHA-256, and applies the profile. It makes no network call where you run it.

<Steps>

1. **Download and verify `checksums.txt`** from the release that matches your `vps-ready version`, as in [Verify a release](/docs/install/#verify-a-release). The hashes in the user-data come from this file, so verify it first.

2. **Write a profile that lists your SSH keys.** At first boot there is no SSH session to copy keys from.

   ```toml
   # vps-ready.toml
   schema = 1
   extends = "web"

   [modules."user.admin"]
   name = "admin"
   authorized_keys = ["ssh-ed25519 AAAAC3Nza... me@laptop"]
   ```

3. **Export it** to a user-data file:

   ```sh
   vps-ready export cloud-init --profile vps-ready.toml --checksums checksums.txt > user-data.yaml
   ```

   Paste `user-data.yaml` into the provider's user-data (or cloud-init) field. It is plain `#cloud-config` and far below the usual 16 KB limit.

4. **Keep the provider's firewall closed, and do not log in, until first boot finishes.** The image's own SSH settings apply for the first minute or so, until cloud-init's last stage runs. Any login during that time, including a provisioning tool that waits for SSH, makes the apply refuse `--deadman=off`.

   Watch the server's console log in the provider's panel (often called the serial or boot log) for cloud-init's final message, `Cloud-init v. ... finished at ...`. The output of the apply comes just before it.

5. **Open the provider's firewall for SSH, then check that it worked:**

   ```sh
   ssh admin@203.0.113.10
   cloud-init status
   sudo vps-ready history
   ```

   `cloud-init status` should say `done`, and `history` should show one transaction `applied (without the timer)`. Open any other ports only after this check.

</Steps>

The exported script runs `vps-ready apply --profile /etc/vps-ready/profile.toml --yes --deadman=off`. Nobody is logged in to confirm at first boot, so it applies without the [safety timer](/docs/guides/safety-net/). The checks that run before any change still apply: a sudo admin with a key exists before root and password logins are turned off, and the SSH port stays open.

If something fails (a download, the hash, a login during first boot, the apply), the server keeps the image's defaults and is not hardened. `cloud-init status` then shows `error`, and `/var/log/cloud-init-output.log` says why. Fix the cause and create the server again.

`export` refuses four kinds of profile:

- `user.admin` without `authorized_keys`. Add your public keys to the profile.
- `net.tailscale` with `auth_key_file`. Any process on the server can read user-data through the provider's metadata service, so it must not lead to a key. Leave the key out, and log in with `sudo tailscale up --accept-dns=false` after the first boot.
- `firewall.inbound` with an explicit `ssh_via`, such as `"tailscale0"`. No SSH session can come through the VPN at first boot, so apply it later, from a session through the VPN.
- `net.tunnel` with `token_file`, for the same reason as Tailscale's key. Leave it out, and after the first boot save the token to a root-only file, set `token_file` and apply again.

The [`private` profile](#the-private-profile) does export: its `ssh_via = "vpn"` stays in step 1 at first boot, with public SSH open.

Flags and exit codes: [`export cloud-init`](/docs/reference/commands/#vps-ready-export-cloud-init).

## Join a private network

`ssh_via` works with any network interface the server has, so you can use one of the modules below or set up a VPN yourself.

### SSH over Tailscale

Add `net.tailscale` to your profile. It installs Tailscale from Tailscale's own repository, keeps `tailscaled` running, and adds Tailscale to automatic updates. It opens no port, because Tailscale needs none.

```toml
[modules."net.tailscale"]
auth_key_file = "/root/tailscale-auth-key"   # optional
```

To join the tailnet without a login prompt, put an auth key in a file only root can read, then apply:

```sh
sudo sh -c 'umask 077; cat > /root/tailscale-auth-key'   # paste <auth key>, then Ctrl-D
sudo vps-ready apply --profile vps-ready.toml
```

`tailscale up` reads the file itself, so the key never shows up in the plan, the journal or the process list. The file must be a regular file owned by root with mode `0600`, not a symlink, in directories only root can write to; otherwise the plan refuses it. Delete the file after the login; later applies use the node's own login.

If you would rather log in yourself, leave `auth_key_file` out. The apply installs and starts Tailscale, and the plan tells you to run:

```sh
sudo tailscale up --accept-dns=false
```

Use a tagged key that is not ephemeral. A tagged node has key expiry off, and an ephemeral node is removed from the tailnet when it goes idle, for example during an outage. If your node's key does expire, `ssh_via` refuses to close public SSH until you turn off key expiry for this machine in the Tailscale admin console.

vps-ready never turns on Tailscale SSH and never accepts the tailnet's DNS settings. A node you already logged in by hand is left as it is. More detail: [`net.tailscale`](/docs/guides/profiles-and-modules/#nettailscale-tailscale).

### SSH over WireGuard

Add `net.wireguard` to run a WireGuard interface, `wg0`, on the server. It installs `wireguard-tools`, makes the server's private key on the server (it never passes through vps-ready), and keeps `wg-quick@wg0` running. `firewall.inbound` opens its UDP port, 51820 by default. It is for admin access to this server only, so your devices reach the server's tunnel address and nothing else.

<Steps>

1. **Make a key pair on each device** you will connect from, and keep the private key there:

   ```sh
   (umask 077; wg genkey | tee laptop.key | wg pubkey)
   ```

   The WireGuard app's "Add tunnel" does the same. Only the public key, which `wg pubkey` prints, goes into the profile.

2. **List the device as a peer.** `host` is the last part of its tunnel address, from 2 to 254, and the server is `.1`:

   ```toml
   [modules."net.wireguard"]
   endpoint = "203.0.113.10"   # optional: the address the device connects to
   peers = [
     { name = "laptop", public_key = "<public key of the laptop>", host = 2 },
   ]
   ```

   Without `address`, the server's subnet is a `/24` in `10.0.0.0/8` derived from `/etc/machine-id`, so each server gets its own. The examples below use `10.86.12.1/24`.

3. **Apply** from your public SSH login, with `firewall.inbound` in the same profile (the `minimal` and `web` profiles have it):

   ```sh
   sudo vps-ready apply --profile vps-ready.toml
   ```

   With `firewall.inbound` in the change, the apply arms the safety timer, so confirm from a new SSH login as usual, which still works through the public address. The client configs print before the confirm. To print them again, for all peers or one, run:

   ```sh
   sudo vps-ready wireguard-config laptop
   ```

   ```ini
   # laptop: the client config, for the WireGuard app or /etc/wireguard/wg0.conf there
   [Interface]
   PrivateKey = <the private key of laptop, which stays on that device>
   Address = 10.86.12.2/32

   [Peer]
   PublicKey = <public key of the server>
   Endpoint = 203.0.113.10:51820
   AllowedIPs = 10.86.12.1/32
   PersistentKeepalive = 25
   ```

   Without `endpoint`, the address comes from your SSH session or the default route, and the command says on stderr when the server has no public address of its own.

4. **Connect.** Paste the config into the WireGuard app (or save it as `/etc/wireguard/wg0.conf` on a Linux device) and replace the placeholder after `PrivateKey =` with the contents of `laptop.key`. Turn the tunnel on (on Linux, `sudo wg-quick up wg0`), then log in through it:

   ```sh
   ssh admin@10.86.12.1
   ```

   `sudo wg show wg0` on the server lists the peer with a recent handshake.

</Steps>

Then close public SSH as in [Close public SSH](#close-public-ssh-port-22-to-the-internet), from the session you just opened, with `ssh_via = "wg0"` and the server's tunnel address (`10.86.12.1` here) in the confirm command:

```toml
[modules."firewall.inbound"]
allow = ["80/tcp", "443/tcp", "443/udp"]
ssh_via = "wg0"
```

vps-ready refuses `ssh_via = "wg0"` unless `wg-quick@wg0` is enabled, which `net.wireguard` does. While SSH depends on `wg0`, any change `net.wireguard` plans arms the safety timer and needs a confirm through `wg0`, and removing the peer your session comes through, or changing its key or `host`, is refused. After `rollback`, the generated server key stays so that client configs keep working: `sudo rm /etc/wireguard/wg0.key` and apply again for a new one. Every device then needs the new public key in its config, so do this while SSH does not depend on `wg0`. More detail: [`net.wireguard`](/docs/guides/profiles-and-modules/#netwireguard-wireguard).

### Another VPN

Any interface works: a `wg0` you set up with `wg-quick`, or the interface of another mesh VPN. Make sure it comes back after a reboot (for `wg0`, `sudo systemctl enable wg-quick@wg0`). For `tailscaled` and `wg-quick@<interface>`, vps-ready checks that; for other interfaces it cannot tell, and the plan says so.

## Close public SSH (port 22) to the internet

`ssh_via` limits the firewall's SSH rule to one interface. Everything else in `firewall.inbound` stays the same, and the SSH server itself is not changed. It takes two applies, so that the private path carries a real login before public SSH closes.

<Steps>

1. **First apply: the VPN and the firewall, without `ssh_via`.** Use your profile with the VPN module and `firewall.inbound`, then confirm as usual. Public SSH stays open. The firewall must be loaded before the next step, so that your public session is tracked as an established connection.

2. **Log in through the VPN.** From your own computer, use the server's VPN address:

   ```sh
   ssh admin@100.64.0.7
   ```

3. **Add `ssh_via` and apply from that session:**

   ```toml
   [modules."firewall.inbound"]
   allow = ["80/tcp", "443/tcp", "443/udp"]
   ssh_via = "tailscale0"
   ```

   ```sh
   sudo vps-ready apply --profile vps-ready.toml
   ```

   Read the notes in the plan. The last one says how to get back in from the provider's console. SSH ports listed in `allow` (the built-in profiles list `22/tcp`) are left out, with a note.

4. **Confirm from a new login through the VPN.** `apply` prints the exact command, with the VPN address:

   ```sh
   ssh -t -o ControlPath=none -p 22 admin@100.64.0.7 sudo vps-ready confirm
   ```

   If nobody confirms in time, the safety timer rolls back and public SSH opens again.

5. **Check the result:**

   ```sh
   sudo vps-ready audit --all
   ```

   `SSH-009` should pass, and `FW-003` lists what the internet can still reach. See [Check it with audit](#check-it-with-audit).

</Steps>

### The private profile

The built-in [`private` profile](/docs/guides/profiles-and-modules/#the-private-profile) does both applies with one file. Extend it with one VPN module and your keys, then run the same command twice: first from a public SSH login (or at first boot from `export cloud-init`), then from a login through the VPN.

```toml
schema = 1
extends = "private"

[modules."user.admin"]
authorized_keys = ["ssh-ed25519 AAAAC3Nza... me@laptop"]

[modules."net.tailscale"]   # or [modules."net.wireguard"] with its peers
```

```sh
sudo vps-ready apply --profile private.toml
```

The first apply sets up the VPN and keeps SSH public, with the note "step 1 of 2: SSH stays public until you apply this profile again from a login through tailscale0" (`wg0` for WireGuard). The second, from a session through the VPN, closes public SSH with the same checks, timer and confirm as the steps above. It has an empty `allow`: add `"80/tcp", "443/tcp", "443/udp"` for a web app, or serve it through a tunnel and keep `allow` empty, as in [A website with no public port](#a-website-with-no-public-port).

The guided setup (`sudo vps-ready`) asks the same thing as "Private access for SSH": none, Tailscale, or WireGuard on this server. For Tailscale it asks for an auth key, or you log in by hand afterwards. For WireGuard it asks for the device's name and its public key, and the apply prints the client config. A domain for Caddy then adds the [tunnel question](#a-website-with-no-public-port). It asks whether to save your answers to `vps-ready.toml`, then prints the step 2 command. Run `sudo vps-ready` again from a login through the VPN, in the directory that holds that root-owned file, and it offers to apply step 2. If you decline the save, it cannot offer step 2: run the printed command with your profile instead.

### A website with no public port

With a VPN for SSH, a web app is what keeps 80 and 443 open. A [Cloudflare Tunnel](/docs/guides/profiles-and-modules/#nettunnel-cloudflare-tunnel) closes them too: `cloudflared` on the server connects out to Cloudflare, which sends the requests for your domains back through that connection to Caddy on loopback.

| Setup | Open to the internet |
|---|---|
| Tailscale for SSH, a tunnel for the web | No inbound port |
| WireGuard for SSH, a tunnel for the web | UDP 51820 only, which answers nothing without a valid handshake |
| A VPN for SSH, a web app without a tunnel | 80 and 443 |

The domains' DNS must be on Cloudflare. In the Cloudflare dashboard, create a tunnel and copy its token from the install command it shows. Then add the tunnel and `behind_tunnel` to the private profile, and leave `allow` empty:

```toml
schema = 1
extends = "private"

[modules."net.tailscale"]

[modules."net.tunnel"]
token_file = "/etc/vps-ready/cloudflared-token"

[modules."deploy.proxy"]
behind_tunnel = true
sites = [{ domain = "app.example.com", upstream = "127.0.0.1:8080" }]
```

Save the token to `token_file` in a file only root can read, and apply:

```sh
sudo install -d -m 0755 /etc/vps-ready
sudo sh -c 'umask 077; cat > /etc/vps-ready/cloudflared-token'   # paste <token>, then Ctrl-D
sudo vps-ready apply --profile private.toml
```

The plan then says which published route to give the tunnel in the dashboard for each site, such as `app.example.com` to `http://127.0.0.1:80`. The connector's start waits for its first connection to Cloudflare, so a bad token or a blocked outbound port 7844 fails the apply, which rolls back the whole transaction, the SSH hardening included.

The guided setup asks this for you. On the `private` profile, a domain for Caddy adds one question:

```text
? How do visitors reach this site
  > Through a Cloudflare Tunnel (no public ports; DNS on Cloudflare)
    Directly, on ports 80 and 443 (Caddy gets the certificate)
? Tunnel token (hidden; Enter to add it later):
```

The tunnel choice adds `net.tunnel` and `behind_tunnel = true` and opens no port. The token is not shown as you type it, and it is asked again unless it decodes as cloudflared decodes it; pasting the whole install command works too. Before the plan, the wizard creates `/etc/vps-ready/cloudflared-token` as a new, empty file owned by root with mode `0600`; it writes the token there only after you answer `y`, outside the transaction, so the journal never holds a copy and a rollback keeps it. Unlike a Tailscale auth key, the connector reads it again at every start, so it stays after the apply. If you decline, stop the wizard, or the plan fails, no token is written; the empty file is removed when the wizard can (Ctrl-C at `Apply N changes?` leaves it, and the next run reuses it). When the file holds a token already, the wizard offers to keep it; a replacement is written only after the `y`, so declining keeps the old one, and if the connector already runs, restart it afterwards with `sudo systemctl restart vps-ready-cloudflared`. A file at that path that others can read, or that is not root's, is refused: fix its owner and mode or move it away first. Enter instead of a token adds `net.tunnel` without `token_file`: the plan says how to add one later. Outside the `private` profile the question is not asked, but a profile file can combine the same modules. Nor is it asked when a cloudflared unit that vps-ready did not write exists, such as `cloudflared.service` from Cloudflare's own install: `net.tunnel` leaves that setup alone, and `behind_tunnel` works with it.

The tunnel's routes are set at Cloudflare, so whoever controls the account can route the internet to anything the server reaches on loopback, SSH included. Turn on two-factor login for the account, and add no routes but the web ones.

### Why the second apply must come through the VPN

After `ssh_via`, a broken VPN means no SSH at all. So vps-ready closes public SSH only when the private path has already carried a real login: yours. The confirm then proves that a new login through the VPN works under the new rules. It does not prove that public SSH is closed; the check after apply does that, by reading the firewall back.

### What it refuses

The plan refuses `ssh_via` when:

- the interface does not exist, is down, or has no address;
- you are not in an SSH session (the console, cloud-init);
- your session did not come in through the interface. The message gives the command to use, for example `ssh -t admin@100.64.0.7 sudo vps-ready apply ...`. With the `private` profile's `ssh_via = "vpn"`, this is the step 1 note instead, and SSH stays public;
- your session comes from the server itself (a login to its own VPN address goes over loopback);
- the unit that brings the interface up at boot (`tailscaled` or `wg-quick@<interface>`) is not enabled;
- the Tailscale node's key expires, Tailscale is not running, or its state is unknown;
- the interface is loopback, a bridge for local containers or guests (`docker0`, `br-*`, `virbr*`, `lxcbr*`, `podman*`, `cni*`, `veth*`), or holds the server's default route;
- you pass `--deadman=off`.

When the loaded firewall already limits SSH to the same interface and SSH ports, all but the last two become notes. That way an apply from the console still works while the VPN is down.

### The confirm through the VPN

`confirm` adds one rule to the [usual ones](/docs/guides/safety-net/#what-counts-as-a-new-login): the new login must connect to an address of the `ssh_via` interface. A login to the public address is refused:

```text
error: this SSH login connected to 203.0.113.10, which is not an address of tailscale0; log in through tailscale0: `ssh -t -o ControlPath=none -p 22 admin@100.64.0.7 sudo vps-ready confirm`
```

### Later changes

While SSH depends on the VPN, any change to it is as risky as closing public SSH:

- A change that `net.tailscale` or `net.wireguard` plans arms the safety timer and needs a confirm through the VPN.
- Every change that arms the timer needs a confirm through the VPN, unless the change removes `ssh_via`. One applied from the console while the VPN is down rolls back at its deadline.
- `--deadman=off` is refused when the plan arms the timer.
- An apply without `ssh_via` opens public SSH again, behind the timer like any firewall change.

## Check it with audit

Three controls show the result. `FW-003` and `SSH-009` are low severity with no automatic fix; `NET-008` is medium and `net.wireguard` fixes it.

- **`FW-003` Only expected ports are open to the internet.** It lists every port the server's firewall lets in from outside, with its process. It fails only on ports other than SSH, 80 and 443, the DHCP clients and WireGuard. Ports open only on a VPN or a Docker bridge do not count. It cannot see a firewall at your provider.
- **`SSH-009` SSH reachable only through a private network.** It passes when the firewall drops by default and accepts SSH only on a VPN interface. It is skipped on servers without a VPN interface. It fails when SSH is limited to an interface that is missing or down, and whenever a VPN interface exists but SSH is still accepted elsewhere: after step 1 (VPN joined, SSH public), that failure is expected and clears after the close step. When SSH is limited to Tailscale, it carries a warning when the node's key expires (with the date), when Tailscale is not running, or when its state is unknown. `detect` shows the same warning.

- **`NET-008` WireGuard private keys readable only by root.** It fails when a file in `/etc/wireguard` is readable by anyone but root. It is skipped when that directory does not exist.

Full list: [Security controls](/docs/reference/security-controls/).

## If the VPN stops working

With `ssh_via`, a broken VPN closes SSH, so plan your way back in before you need it.

**Set a password for a sudo user before you close public SSH.** The provider's web console logs in with a password, and without one, recovery needs the provider's rescue mode.

<Steps>

1. **Set the password** from your current login:

   ```sh
   sudo passwd admin
   ```

   The SSH server still refuses passwords; only the console uses it.

2. **Log in from the provider's web console and roll back the `ssh_via` change**, by its ID. This reopens public SSH, and the firewall stays loaded:

   ```sh
   sudo vps-ready history
   sudo vps-ready rollback --txn <id>
   ```

3. **If the rollback refuses**, remove `ssh_via` from your profile (or switch to one without it) and apply from the console. The plan reopens public SSH behind the safety timer, and you confirm from a new public login, not through the VPN:

   ```sh
   sudo vps-ready apply --profile vps-ready.toml
   ssh -t -o ControlPath=none -p 22 admin@203.0.113.10 sudo vps-ready confirm   # from your computer
   ```

4. **Last resort: stop the firewall.** This drops every rule until the next boot. Load it again as soon as SSH works:

   ```sh
   sudo systemctl stop vps-ready-firewall
   # roll back or apply as above, then:
   sudo systemctl start vps-ready-firewall
   ```

</Steps>

A manual rollback can refuse while SSH depends on the VPN:

- When it would limit SSH to the VPN again, with no timer to undo it. Run it from an SSH login through the VPN, from another machine.
- When it would stop `tailscaled` or `wg-quick@wg0`, or take the node off the tailnet, while SSH depends on that VPN. Remove `ssh_via` first, or roll back the transaction that set it.
- When it would cut your own session, which comes through the VPN (for WireGuard, by stopping `wg-quick@wg0` or removing your peer). Run it from the console or a public SSH login.
