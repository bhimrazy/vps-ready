The install script downloads the release tarball for the machine, checks it against the SHA-256 embedded in the script, verifies the release signature when `gh` or `cosign` is installed, and copies the binary to `/usr/local/bin`. [View the install script](https://github.com/bhimrazy/vps-ready/releases/latest/download/install.sh).

| Option | What it does |
|---|---|
| `--dry-run` | Show what would be done, change nothing |
| `--prefix DIR` | Install directory (default: `/usr/local/bin`) |
| `--version` | Print the version the script installs and exit |

The command is also installed as `vpsready`, without the hyphen.

<Aside type="caution" title="Where the binary lives matters">
The safety timer runs the binary as root later, so `apply` refuses the admin user, SSH server config and firewall modules when the binary is under `/home`, `/tmp`, `/var/tmp` or `/dev/shm`, or when it or a parent directory is writable by anyone but root. The install script's `/usr/local/bin` is fine. A `cargo install` as a normal user lands in `~/.cargo/bin`, so copy the binary to `/usr/local/bin` before you use a profile.
</Aside>

Building with `cargo` needs a Rust toolchain on the server.

## The .deb package

From v0.5.0, each release has `vps-ready_<version>_amd64.deb` and `vps-ready_<version>_arm64.deb`, for Debian and Ubuntu. They hold the same binary as the tarball, installed to `/usr/bin/vps-ready` with the `vpsready` link. The package has no install scripts: installing it changes nothing else on the system.

The `.deb` is not signed on its own, and apt does not check a signature on a file you install by path. It is covered by the release's `checksums.txt`, so run the checksum step from [Verify a release by hand](#verify-a-release-by-hand) first, then:

```sh
sudo apt install ./vps-ready_<version>_amd64.deb
```

There is no apt repository, so `apt upgrade` does not update it: install the newer `.deb` the same way. There are no `.rpm` or `.apk` packages, because vps-ready runs only on Debian and Ubuntu.

### Moving from the install script

`/usr/local/bin` comes before `/usr/bin` on `PATH`, so a binary left by `install.sh` would keep running instead of the package. Remove it first:

```sh
sudo rm /usr/local/bin/vps-ready /usr/local/bin/vpsready
sudo apt install ./vps-ready_<version>_amd64.deb
hash -r
```

`vps-ready version` warns when it finds another `vps-ready` on `PATH` (`warning: another vps-ready is installed at <path>`), and the first one on `PATH` is the one that runs. A pending safety timer is not affected by the move: it runs a private copy of the binary that applied, kept in `/var/lib/vps-ready/bin`.

## Check the install

```sh
vps-ready --version
sudo vps-ready detect
```

`detect` only reads: it prints the distro, init system, virtualization, effective SSH server config and listening ports. Next, run the [Quick start](/docs/quick-start/), which starts with `sudo vps-ready`, the guided setup.

## Upgrade

vps-ready never updates itself: it makes no network calls except package installs. To upgrade, run the same installer again. It writes the new binary next to the old one and renames it into place, so the swap is atomic.

<Command lines={[`curl -fsSL ${script} | sudo sh`]} />

Check with `vps-ready --version`, and see the [releases](https://github.com/bhimrazy/vps-ready/releases) for what changed. The installer only replaces the binary; your journal in `/var/lib/vps-ready` stays, so `history` and `rollback --last` keep working.

To pin a version or read the script first, download the versioned installer from its release instead of `latest`, for example <code>{`https://github.com/bhimrazy/vps-ready/releases/download/v${VERSION}/install.sh`}</code>.

## Verify a release by hand

Every release ships `checksums.txt` (which lists the tarballs, the `.deb` files and the SBOM), a Sigstore bundle for it, and a GitHub build-provenance attestation for each tarball and `.deb` file and for `install.sh`.

```sh
# 1. Checksums
sha256sum --check --ignore-missing checksums.txt

# 2. Signature on the checksums (keyless, signed by the release workflow)
cosign verify-blob \
  --bundle checksums.txt.sigstore.json \
  --certificate-identity-regexp '^https://github.com/bhimrazy/vps-ready/\.github/workflows/release\.yml@refs/tags/v' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  checksums.txt

# 3. Build provenance for a tarball or a .deb
gh attestation verify vps-ready-<version>-<target>.tar.gz --repo bhimrazy/vps-ready
gh attestation verify vps-ready_<version>_amd64.deb --repo bhimrazy/vps-ready
```

### The SBOM

Each release also has `vps-ready-<version>.cdx.json`, a CycloneDX 1.5 list of the crates the binary is built from. It is listed in `checksums.txt`, and attested as a second attestation on the tarballs and `.deb` files, with the SBOM as its predicate. `gh` checks the SLSA provenance by default, so name the CycloneDX predicate type to check the SBOM's attestation:

```sh
gh attestation verify vps-ready_<version>_amd64.deb \
  --repo bhimrazy/vps-ready \
  --predicate-type https://cyclonedx.org/bom
```

Add `--format json` to print what the attestation carries and compare it with the SBOM you downloaded.

The trust model of each install channel is in [Supply chain and release](/docs/project/release/).
