vps-ready is one static binary for Linux on x86_64 and arm64, with nothing else to install. The install script is the common way; a `.deb` package and `cargo` work too. Run these on the server. The install script is three steps on purpose: download, read, run.

<Tabs syncKey="install">
  <TabItem label="install script">
    <Command lines={[`curl -fsSLO ${script}`, 'less install.sh', 'sudo sh install.sh']} />
  </TabItem>
  <TabItem label=".deb">
    <Command lines={[`curl -fsSLO ${RELEASE_BASE}/${RELEASE_ASSETS[0].deb}`, `sudo apt install ./${RELEASE_ASSETS[0].deb}`]} />
  </TabItem>
  <TabItem label="cargo">
    <Command lines={['cargo install vps-ready --locked']} />
  </TabItem>
</Tabs>

Then try it read-only. `audit` reports what fails, and `plan` shows what would change; neither writes anything:

<Command lines={['sudo vps-ready audit', 'sudo vps-ready plan']} />

The install script downloads the release tarball for the machine, checks it against the SHA-256 embedded in the script, verifies the release signature when `gh` or `cosign` is installed, and copies the binary to `/usr/local/bin`. <a href={script}>View the install script</a>. The `.deb` tab is for x86_64; the [download table](#download-a-release) has the arm64 package.

If `cosign`, or `gh` while logged in (`gh auth status`), is installed and the signature check fails, the install stops (use `--skip-verify` to override). A `gh` that is not logged in is skipped. With no usable tool, the script says so and continues: the binary is then checked only against the checksums embedded in the script, so [verify the script itself](#verify-a-release) if that matters to you.

| Option | What it does |
|---|---|
| `--dry-run` | Show what would be done, change nothing |
| `--prefix DIR` | Install directory (default: `/usr/local/bin`). Refused when group- or other-writable |
| `--skip-verify` | Install even if the signature check fails; the SHA-256 check still runs |
| `--version` | Print the version the script installs and exit |

The command is also installed as `vpsready`, without the hyphen.

Where the binary lives matters, because the safety timer runs it as root later. `apply` refuses the admin user, SSH server config and firewall modules when the binary is under `/home`, `/tmp`, `/var/tmp` or `/dev/shm`, or when it or a parent directory is writable by anyone but root. The install script's `/usr/local/bin` and the `.deb`'s `/usr/bin` are fine. Building with `cargo` needs a Rust toolchain on the server, and a `cargo install` as a normal user lands in `~/.cargo/bin`, so copy the binary to `/usr/local/bin` before you use a profile.

## Verify a release

Every release ships `checksums.txt`, which lists the tarballs, the `.deb` files, `install.sh` and the SBOM. The release workflow signs it with Sigstore, and attests the build provenance of each of those files. Check them in this order: the signature on `checksums.txt` first, then each file against it.

Download `checksums.txt`, its bundle and the files you want from the same release, here `install.sh` and the x86_64 `.deb`:

<Command lines={[
  `B=${RELEASE_BASE}`,
  `curl -fsSLO $B/checksums.txt -O $B/checksums.txt.sigstore.json -O $B/install.sh -O $B/${RELEASE_ASSETS[0].deb}`,
]} />

To check that `checksums.txt` was signed by the release workflow for this exact tag, run:

<Command lines={[
  `cosign verify-blob --bundle checksums.txt.sigstore.json --certificate-identity ${identity} --certificate-oidc-issuer https://token.actions.githubusercontent.com checksums.txt`,
]} />

Then check every file you downloaded against it. Each prints `OK`:

<Command lines={['sha256sum --check --ignore-missing checksums.txt']} />

With `gh`, you can also check each file's build provenance. The flags pin it to this repository's release workflow and the tag, so a file built by any other workflow or from any other ref fails:

<Command lines={[
  `gh attestation verify install.sh ${attest}`,
  `gh attestation verify ${RELEASE_ASSETS[0].deb} ${attest}`,
]} />

The same command works for a tarball or the SBOM. Without `cosign`, run it on each file you downloaded instead of the two steps above.

### Check the SBOM

Each release also has `vps-ready-<version>.cdx.json`, a CycloneDX 1.5 list of the crates the binary is built from. It is listed in `checksums.txt`, and attested as a second attestation on the tarballs and `.deb` files, with the SBOM as its predicate. `gh` checks the SLSA provenance by default, so name the CycloneDX predicate type to check the SBOM's attestation:

<Command lines={[`gh attestation verify ${RELEASE_ASSETS[0].deb} ${attest} --predicate-type https://cyclonedx.org/bom`]} />

Add `--format json` to print what the attestation carries and compare it with the SBOM you downloaded. The trust model of each install channel is in [Supply chain and release](/docs/project/release/).

## Check the install

To check the version and what vps-ready sees on this server, run:

```sh
vps-ready --version
sudo vps-ready detect
```

`detect` only reads: it prints the distro, init system, virtualization, effective SSH server config and listening ports.

## Upgrade

vps-ready never updates itself, since it makes no network calls except package installs. To upgrade, download, read and run the new release's installer:

<Command lines={[`curl -fsSLO ${script}`, 'less install.sh', 'sudo sh install.sh']} />

It writes the new binary next to the old one and renames it into place, so the swap is atomic. Check with `vps-ready --version`, and see the [releases](https://github.com/bhimrazy/vps-ready/releases) for what changed. The installer only replaces the binary; your journal in `/var/lib/vps-ready` stays, so `history` and `rollback --last` keep working.

Each installer installs the version it was released with, so the URL above pins v{VERSION}. Replace the version in it to install another release.

## Install the .deb package

From v0.5.0, each release has `vps-ready_<version>_amd64.deb` and `vps-ready_<version>_arm64.deb`, for Debian and Ubuntu. They hold the same binary as the tarball, installed to `/usr/bin/vps-ready` with the `vpsready` link. The package has no install scripts, so installing it changes nothing else on the system.

The `.deb` is not signed on its own, and apt does not check a signature on a file you install by path. It is covered by the release's `checksums.txt`, so [verify the release](#verify-a-release) first, then install it:

<Command lines={[`sudo apt install ./${RELEASE_ASSETS[0].deb}`]} />

There is no apt repository, so `apt upgrade` does not update it: download, verify and install the newer `.deb` the same way. There are no `.rpm` or `.apk` packages, because vps-ready runs only on Debian and Ubuntu.

### Moving from the install script

`/usr/local/bin` comes before `/usr/bin` on `PATH`, so a binary left by `install.sh` would keep running instead of the package. Remove it first:

```sh
sudo rm /usr/local/bin/vps-ready /usr/local/bin/vpsready
sudo apt install ./vps-ready_<version>_amd64.deb
hash -r
```

`vps-ready version` warns when it finds another `vps-ready` on `PATH` (`warning: another vps-ready is installed at <path>`), and the first one on `PATH` is the one that runs. A pending safety timer is not affected by the move, because it runs a private copy of the binary that applied, kept in `/var/lib/vps-ready/bin`.
