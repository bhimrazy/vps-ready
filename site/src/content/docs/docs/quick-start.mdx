This page takes a fresh server from its first audit to hardening you have confirmed. The guided setup asks a few questions and does the rest; the step-by-step way runs each stage yourself. Either way, changes that could lock you out roll back on their own unless a new login confirms them.

Run these on the server, as root or with `sudo`.

## The guided way

To start the guided setup, run vps-ready with no arguments on a terminal:

```sh
sudo vps-ready
```

It checks that you are root and that the binary can run from the [safety timer](/docs/guides/safety-net/), then looks at the server and asks:

```text
? What will this server run?
  > Web apps or Docker: opens ports 80 and 443 (recommended: Docker is installed)
    Something else: only SSH is open
? Admin user for logging in: admin
? Private access for SSH
  > None: SSH stays reachable from the internet, with keys only
    Tailscale (the private profile)
    WireGuard on this server (the private profile)
? Open ports besides SSH (22, always open) (Space toggles, Enter continues)
  [x] 80/tcp
  [x] 443/tcp
  [x] 443/udp
? Pick which modules to run yourself? (y/N) no
Caddy can serve your apps over HTTPS and get their certificates. Each domain
needs a DNS record for this server.
? Domain to serve, e.g. app.example.com (Enter for none): app.example.com
? Address of the app behind app.example.com, e.g. 127.0.0.1:8080: 127.0.0.1:8080
? Another domain (Enter for no more):
```

- The recommended answer comes first and says why.
- The admin line says whether the name is a new or an existing account, and which SSH keys it gets.
- Tailscale or WireGuard moves the answers onto the `private` profile, which closes SSH to the internet in a second apply, from a login through the VPN. [Private access](/docs/guides/private-access/) walks through it.
- On the `private` profile, a domain adds the question "How do visitors reach this site": through a Cloudflare Tunnel, with no public port and a hidden token prompt, or directly on 80 and 443. New in v0.7.0; see [A website with no public port](/docs/guides/private-access/#a-website-with-no-public-port).
- Ports that something listens on are offered unchecked; unchecked ports are blocked.
- `y` to the module question lets you pick modules one by one.
- The Caddy questions appear when Docker is part of the setup, or when you tick `deploy.proxy` in the module list. Press Enter at the first one to skip Caddy. A domain with an upstream adds the `deploy.proxy` module, and a bad domain, a duplicate, or an upstream written as `localhost:8080` is asked again with the reason. See [Deploy an app](/docs/guides/deployment-modules/#caddy-with-domains-and-upstreams).

Then it shows the same plan as `apply`, asks `Apply N changes? [y/N]` and applies behind the safety timer. Confirm from a new login, as in [step 4](#step-by-step) below. It ends with the `sudo vps-ready apply --profile ...` command that repeats the setup without questions, and offers to save your answers to `vps-ready.toml` when they differ from a built-in profile.

Ctrl-C at a question stops with `Nothing was changed.` To read what a module does first, run `vps-ready modules ssh.server` ([reference](/docs/reference/commands/#vps-ready-modules)).

## Step by step

This is the same flow without the questions. The first two steps change nothing, so you can stop after either one.

<Steps>

1. **Audit: see what fails.** To list the controls that fail or could not be checked, run:

   ```sh
   sudo vps-ready audit
   ```

   Each one comes with the reason it matters and, when a module can fix it, the command that does. `--all` also lists the passing ones, and `--json` prints everything for CI. The end of a real run:

   ```text
   5 passed, 5 failed (1 high, 3 medium, 1 low), 0 unknown, 19 skipped
   Skipped: kernel settings are not checked inside a container.
   Skipped: Docker is not installed.
   vps-ready can fix all 5 (SSH-002, FW-001, SSH-001, UPD-001, SSH-005): run `sudo
   vps-ready plan --module ssh.server --module firewall.inbound --module
   updates.auto`.
   ```

2. **Plan: read what would change.** To see a diff of every file and setting, grouped by module, run:

   ```sh
   sudo vps-ready plan --profile minimal
   ```

   Each module lists the controls it fixes and labels each change with its reversibility. Nothing is written. Without `--profile`, `plan` and `apply` cover only kernel settings and automatic updates, which cannot lock you out.

3. **Apply: make the changes.** To apply, run:

   ```sh
   sudo vps-ready apply --profile minimal
   ```

   `apply` prints the plan again and asks before it changes anything (`Apply 16 changes? [y/N]`). With `minimal` or `web` it arms the safety timer before the first change, makes the changes, and then ends like this, with your own admin user, address and port:

   ```text
   Changes are live. To keep them, open a NEW terminal on your computer and run
   this to show you can still log in:

       ssh -t -o ControlPath=none -p 22 admin@203.0.113.10 sudo vps-ready confirm

   If no new session confirms by 14:07:30 UTC (5:00 left), every change is rolled back.
   More time: sudo vps-ready confirm --extend
   Do not edit files vps-ready manages until you confirm: an unconfirmed change reverts them.
   Ctrl-C stops waiting here, not the timer.
   ```

4. **Confirm: prove a new login works.** Copy that `ssh` line into a **new** terminal on your own computer. If the login works, `confirm` succeeds, the first terminal prints `Confirmed: the changes of transaction ... stay` and `apply` exits 0.

   **Your open terminal proves nothing**, because SSH server reloads and connection tracking keep existing sessions alive. Only a new login counts; see [How the safety net works](/docs/guides/safety-net/). If the new login fails, do nothing: when the timer runs out (or at the next boot) every change is rolled back and your old login works again.

5. **Undo: whenever you want.** Every change is journaled, so you can undo a transaction at any time, not only while the safety timer runs:

   ```sh
   sudo vps-ready history          # list transactions, newest first
   sudo vps-ready rollback --last  # undo the last one
   ```

</Steps>
